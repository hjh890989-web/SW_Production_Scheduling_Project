# EVS 경량화 전환 계획 v1.0

> Docker 풀스택 운영 → **단일 Node 프로세스(SQLite)** 경량 구동 전환 및 **RBAC 4-Role 축소**
> 작성일: 2026-06-18 · 상태: 승인 대기

---

## 1. 배경 및 목적

EVS는 자매 서비스(FCB 유류비 정산·EGS 경비 청구, Python Flask + SQLite, `python run.py` 단일 프로세스)와 달리
Docker Compose 6~9개 서비스(app·postgres·prometheus·loki·promtail·grafana·(운영) nginx·minio·solver)로 구동된다.

이 무게는 취향이 아니라 **설계 문서로 강제된 요구사항**에 묶여 있었다(아래 §2). 그러나 운영 정책이 다음과 같이 변경되면서
해당 요구사항이 모두 해소되어, **FCB/EGS 동급의 경량 구조로 전환**한다.

### 운영 정책 변경 (전제)
| 변경 항목 | 결정 |
|---|---|
| Audit 5년 보존 | **불필요** |
| KSF 자동 측정(관측 스택) | **불필요** |
| 동시 사용자 | **10명 이내**로 제한 |
| 사용 주체 | **생산관리자의 스케줄 생성에 주력** |
| 성형/압출 반장 수정 권한 | **삭제** (Role 완전 제거) |

## 2. 기존 무게의 근거와 해소

설계 문서(Stage_A 개발계획서 v1.3, Stage_C PRD v1.4, Stage_D 이슈, 의사결정 로그) 확인 결과,
각 구성 요소는 아래 요구사항에 결합되어 있었고 정책 변경으로 모두 해소된다.

| 구성 요소 | 강제했던 요구사항 (결정 ID) | 해소 사유 |
|---|---|---|
| PostgreSQL (운영) | Audit 5년 보존(R-13, OEM 추적), KSF 일일 스냅샷 집계, 동시 드래그 row-level 락 (D-19) | Audit·KSF 불필요 + 동시성 10명 이내 → SQLite로 충분 |
| Grafana·Loki·Prometheus·promtail | 사내망 전용(외부 SaaS 금지, D-8) + KSF-3 "변동 영향 ≤5초" 자동 측정 (PRD §5.5) | KSF 자동 측정 불필요 |
| Docker Compose | 12-Factor·Cloud-Ready 향후 클라우드 이전 대비 (D-20) | 사내 단일 PC 구동에는 과함 |
| Python OR-Tools 솔버 | 룰베이스 한계 보완(다이/노즐 -30% 잔여분) (Sprint 12) | 룰 fallback 내장 → 미가동해도 동작 |
| 성형/압출 반장 Role | F-3 수동 보정(드래그 재배분, J-MR-2 핵심 성공 지표) | 생산관리자 단독 운영으로 정책 변경 |

## 3. 목표 아키텍처

| 영역 | 현재 | 경량화 후 |
|---|---|---|
| 실행 | Docker Compose 6~9 서비스 | **단일 Node 프로세스** (`next start`) |
| DB | PostgreSQL 컨테이너 | **SQLite 파일** (`prisma/evs.db`) |
| 관측 | Grafana·Loki·Prometheus·promtail | **제거**(아카이브) |
| Role | 6종(반장 2종 포함) | **4종**: ADMIN · PRODUCTION_MANAGER · SALES_PURCHASE · EXECUTIVE |
| 솔버 | OR-Tools 컨테이너 | 미가동 → **룰 fallback**(기존 동작 유지) |
| 포트 | 5002 (Docker) | 5002 유지 (`next start -p 5002`) |

→ FCB/EGS의 `python run.py`와 동급. 기동 = 스크립트 한 번.

### 핵심 검증 사실
- **PRODUCTION_MANAGER(생산관리자)는 이미 `molding:write`·`molding:confirm`·`extrusion:write`·`extrusion:confirm` 보유** → 반장 제거 후에도 스케줄 생성·드래그·확정 그대로 동작. (`lib/permissions.ts:34-49`)
- **작업실적 입력(`molding:result`·`extrusion:result`)만 현재 반장 전용** → 이것만 생산관리자로 이관 필요(F-5 MES 자동 동기화라 영향 적음).
- **스키마에 PostgreSQL 전용 타입 전무**(`@db.*`·파티셔닝 없음) → SQLite로 그대로 동작.
- **관측 스택은 앱 코드 의존 0** → `/api/metrics`는 미사용 상태로 무해, KSF cron은 애초에 startup 미등록.

## 4. 실행 계획

### Phase 1 — RBAC 4-Role 축소 (반장 완전 제거)

서버 액션은 Role이 아닌 **권한 문자열**을 검사하고 그 권한을 생산관리자가 이미 보유 → **액션·UI 코드는 미변경**.

| 파일 | 변경 내용 |
|---|---|
| `auth.config.ts` | `ROLES`에서 `MOLDING_LEADER`·`EXTRUSION_LEADER` 제거 |
| `lib/permissions.ts` | 매트릭스에서 두 Role 행 삭제 + **`molding:result`·`extrusion:result`를 PRODUCTION_MANAGER에 추가** |
| `lib/permissions.test.ts` | 4-Role 매트릭스로 테스트 갱신 |
| `prisma/schema.prisma:248` | `role` 기본값 `MOLDING_LEADER` → `PRODUCTION_MANAGER` |
| `prisma/seed-data.ts` | 합성 유저 `90000002`·`90000003`(반장) 제거 |
| `prisma/seed-employees.ts` | `mapEmployeeRole()`의 반장 분기 → **`EXECUTIVE` 반환**으로 변경 |
| 문서 | `CLAUDE.md §2`, `.claude/agents/authjs-rbac.md`, `.agents/rules/004-hitl-and-security.md` Role 표 갱신 |

- 서버 액션(생성·드래그·확정): **변경 없음**(권한 기반 → 자동으로 생산관리자 전용화)
- UI 버튼: **변경 없음**(권한 없으면 액션이 `ForbiddenError` 반환)
- 검증: `npm test`(단위) green

### Phase 2 — 경량 실행 전환 (Docker/Postgres/관측 제거)

1. **운영 경로 폐기** — `Dockerfile`·`scripts/prisma-prod-schema.mjs`·`db:push:prod`·`docker-compose*.yml` 미사용.
   → **삭제 대신 `infrastructure/_archive/`로 이동**해 보존(되돌림 가능).
2. **관측 인프라 아카이브** — `infrastructure/{prometheus,loki,promtail,grafana}/` 이동. **앱 코드 변경 0건.**
3. **라이트 실행 스크립트 작성** — `start-light.ps1`:
   - 포터블 Node(`C:\Users\Administrator\node20`) PATH 주입
   - env 설정: `DATABASE_URL=file:./prisma/evs.db`, `AUTH_SECRET`, `AUTH_URL=http://localhost:5002`, `NODE_ENV=production`
   - 최초 1회: `prisma db push` + `prisma db seed`
   - `next build`(변경 시) → `next start -p 5002`
   - (옵션) FCB 패턴처럼 Windows 시작프로그램 자동 등록 스크립트 추가
4. **`.env` 정리** — SQLite·5002 기준으로 통일, `.env.prod`(Postgres) 아카이브.

### Phase 3 — 데이터 이전 + 검증

- **데이터 이전**: 결재선 엑셀에서 **SQLite로 재시드**(`seed-employees.ts`). (Postgres 덤프 이전보다 단순·안전)
- **기존 반장 계정**: §5 결정에 따라 `EXECUTIVE`로 일회성 업데이트(또는 재시드 시 자동 반영).
- **검증**: `npm test` → `start-light.ps1` 기동 → 로그인·스케줄 생성·드래그·확정·실적 입력 수동 확인.

## 5. 결정 사항

| 항목 | 결정 |
|---|---|
| 경량화 방식 | **전면 경량화 (Docker 제거)** — 운영도 SQLite + 단일 `next start`로 통일 |
| 반장 Role | **완전 제거** (ExtrusionForeman/MoldingForeman = EXTRUSION_LEADER/MOLDING_LEADER) |
| 기존 반장 계정 | **읽기 전용 조회용으로 전환 (EXECUTIVE)** — 현장이 일정·수주 조회는 가능, 편집 불가 |
| 작업실적 권한 | `molding:result`·`extrusion:result`를 **PRODUCTION_MANAGER로 이관** |
| 포트 | 5002 유지 |
| Docker 자산 | 삭제 아님 — `infrastructure/_archive/`로 **보존** |

## 6. 리스크 및 유의사항

- **F-3 수동 보정(반장 드래그)은 본래 핵심 성공 지표(J-MR-2)였음** — 생산관리자 단독 운영으로 제품 범위가 축소됨을 인지. 추후 반장 편집을 되살리려면 Role·권한을 복원하면 됨(가역적).
- **운영 재확대 시**: Audit 5년·KSF 자동 측정 요구가 부활하면 PostgreSQL + 관측 스택이 다시 필요. 이때 아카이브한 Docker 자산을 복원. (스키마는 provider 치환만으로 Postgres 전환 가능 — 코드 무변경)
- **솔버**: `SOLVER_URL` 미설정 시 룰 fallback으로 동작하므로 경량 모드에서 정상. 최적화 품질만 룰 수준.
- **백업**: Postgres `pg_dump` 대신 **SQLite 파일 복사**로 단순화(`prisma/evs.db` 정기 복사).
